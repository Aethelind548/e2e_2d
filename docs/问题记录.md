## P010 `pause.request` 在 Lightning 2.2.1 上不停止训练

状态：`RESOLVED`（2026-10-26，代码与真实 Lightning 回归均已验证；已加载的旧进程需重启才生效）。

**现象：** `cos50` 实验于 14:52:11 提交 `pause.request`，14:52:12 正确写入 `pause-step067668.ckpt`（729 MB，763 张量，`scheduler epochs=50`）与 `state=paused`，但**训练进程继续运行**，GPU 仍为 94%，epoch 27 继续推进 1.5 分钟以上。

**根因：** `on_train_batch_end` 用 `trainer.should_stop = True` 请求停止。Lightning 2.2.1 的 `Trainer` **没有 `should_stop` 属性**（`hasattr(Trainer,'should_stop') == False`），该赋值只在实例上创建一个惰性字段，不产生任何控制效果。`_FitLoop.done` 实际依据 `_is_max_limit_reached(epoch_loop.global_step, epoch_loop.max_steps)` 判断，且 `_FitLoop.max_steps`、`_FitLoop.done` 都是只读 property（无 setter），只有 `epoch_loop.max_steps` 可写。

**修复：** 新增模块级 `request_graceful_stop(trainer)`——保留 `trainer.should_stop = True`（旧版本可能有效）后，把 `trainer.fit_loop.epoch_loop.max_steps` 设为当前 `global_step`，使 `done` 立即为真。`on_train_batch_end` 改调该函数。

**验证：** 真实 Lightning 集成测试（`max_epochs=50`、`limit_val_batches=0`）在第 3 步调用后 `global_step` 精确停在 3，输出 `` `Trainer.fit` stopped: `max_steps=3` reached``。`tests/training` 全量 **146 passed**（新增 2 项）。

**操作影响：** 代码修复只对**新启动**的进程生效——已加载模块的进程仍持有旧 `ExperimentControl`。本次 `cos50` 于 14:55 用 `SIGTERM` 终止主进程，`pause-step067668.ckpt` 完好可恢复（epoch 27 / step 67668 / scheduler `last_epoch=27`、`epochs=50`），`best-025-065104.ckpt`、`best-026-067608.ckpt`、`last.ckpt`（ep26）均保留。GPU 显存由 10.9 GB 释放到 2.4 GB。

**遗留：** 该 checkpoint 的 `scheduler.epochs` 已是 50，续训时 `audit_lr_scale` 不会再触发注入（幂等），属预期行为。

## P012 训练收敛瓶颈：泛化不足与分支失衡

状态：`ACTIVE`（2026-10-26，30 个 epoch 的连续轨迹已给出定位依据；修复方案待执行）。

**现象（armA→contA→cos50→cos50b，ep0–29）：**

| 观察 | 数值 | 说明 |
| --- | --- | --- |
| `train/loss` | 59.46 → **16.91**（−71.6%） | 单调下降，从未出现平台 |
| `val/paper_loss` | 76.49 → **79.39**（ep25–31，+3.8%） | 退火期间持续恶化 |
| train/val 原始口径 gap | 3.17 → 3.86 倍 | 随 epoch 扩大 |
| paper 轨迹项 | 65.75–67.24 震荡 | ep10 以来 19 个 epoch 无突破 |
| paper BEV | 5.68 → **6.22**（+9.5%） | 单调恶化 |
| paper agent_box | 4.41 → 2.98（−32%） | 唯一持续改善 |

**已排除的变量：学习率。** `scheduler_epochs=50` 已让余弦真正走完前半段（ep25–31 LR 从 1.65e-4 降到约 1.05e-4，−36%），`val/paper_loss` 不降反升 3.8%；ep28 的单次下降是噪声，ep29–31 连续反弹。训练数学、数据划分、batch 配置在四阶段中保持不变。低 LR 期间 train 继续下降 24.5%，说明它只是在更深地拟合训练集。

**三个待解决的子问题（按证据强度）：**

1. **泛化不足（主因）** — train −71.6% 而 val 零改善。训练集仅 160,266 帧，官方设计为 100 epoch × 640k 样本 ≈ 64M 遍历，本工程总遍历 ~4M，**只有 1/16**。可选方向：恢复未入划分的 71,286 帧（缺 Target，需重建）、扩充 Route universe、或加强正则（`weight_decay` 1e-4 → 5e-4、head Dropout 0.1 → 0.2、EMA）。
2. **BEV 分支持续恶化** — 梯度实测 `bev_head` 仅占 0.55%（2.35 / 425.7），trajectory 分支占 99.5%。共享 backbone 被轨迹任务垄断，BEV head 得不到有效特征更新。可选方向：BEV head 单独 `lr_mult=0.5`（不改 loss 公式）、或提高 `bev_semantic_weight`（会改变 loss 定义，需重新基线化）。
3. **轨迹项停滞与低速过预测** — 见 P008。oracle ADE 1.09 vs selected 3.11（2.8 倍），说明候选里有更好轨迹但评分头选错；低速段预测行程 1.38–1.63× 真值（41% 样本超 2 倍）。

**下一步约束：**
- 若改动触及 loss 权重（如 `bev_semantic_weight`），`val/paper_loss` 绝对值会变，**必须重新建立基线**，不能与当前 77 比较；
- 若只改正则 / EMA / 分支 lr，公式不变，可直接对比；
- 建议单变量推进，先做「EMA + BEV head `lr_mult=0.5`」这组正交且低风险的改动。

**证据：** 指标轨迹见 [训练主文档](../tools/training/README.md) 的「短程训练结果」节；`cos50b/logs/lightning_logs/version_0/metrics.csv`；梯度构成见 `grad_norms.jsonl`。

## P013 训练进程被 SIGHUP 终止与同目录 resume 崩溃

状态：`FIXED`（2026-10-26，R1 首轮运行时暴露，两处修复均已回归覆盖）。

**现象：** R1 训练在 epoch 0 完整跑完（47:07，生成 `ema-000-002504.ckpt` / `best-000-002504.ckpt` / `last.ckpt`）后，于 epoch 1 的 42%（step 3,560）静默消失。日志无 traceback、`dmesg` 无 OOM 记录、`training_progress.json` 停在 `state=running`。

**根因一：缺 `setsid`/`nohup`。** 启动时把训练作为终端前台进程提交，终端会话销毁时整个进程组收到 SIGHUP。Python 无法捕获该信号，因此不产生任何异常输出。修复：改用 `setsid nohup ... < /dev/null & disown` 提交，进程脱离会话，终端关闭不再影响训练。

**根因二：`output.mkdir(exist_ok=False)` 阻断同目录 resume。** `resume_contract` 设计上**支持**在同目录内 resume（`origin=inside-experiment`），但 `main()` 无条件执行 `mkdir(exist_ok=False)`，导致 resume 到已存在的实验目录时抛 `FileExistsError` 直接退出。修复：抽出 `prepare_output_dir(output, resuming=False)`，`resuming=True` 时允许复用已有目录；fresh run 仍拒绝已存在目录，避免覆盖陈旧实验。同时保留原有的「输出根挂载点缺失即报错」保护。

**恢复代价：** 从 `last.ckpt`（epoch 0 / step 2,504，SHA `3d576a65…`）resume，损失 epoch 1 的前 1,056 个优化步（约 18 分钟）。

**已验证：** `last.ckpt` 内 EMA state 完整（`num_updates=2504`、`decay=0.999`、`shadow` 546 张量），resume 后可继续累积；`ema-000-002504.ckpt` schema `status-ema-weights-v1`、`state_dict` 546 项、243 MB（约 raw 972 MB 的 1/4，因不含优化器状态）。新增回归 `test_prepare_output_dir_allows_same_directory_resume_only`，`tests/training` **152 passed**。

**运维约束：** 训练必须用 `setsid nohup` 提交；启动后用 `pgrep -fc status_experimental_train` 应为 9（1 主 + 8 worker）；进程数为 0 而 `state` 仍为 `running` 说明被外部信号终止，不是正常结束。

## P014 loss 权重变更使 Checkpoint 选择历史失效

状态：`FIXED`（2026-10-27，R2 切换时发现并处理）。

**现象（潜伏型）：** R2 把 `bev_semantic_weight` 从 14 提到 42，`val/paper_loss` 的量级随之从 ~67 抬到 ~83。但 `ModelCheckpoint` 的 `best_k_models` 会在 resume 时从 checkpoint 恢复，其中已有旧口径的三个记录：`best-000` = 121.078、`best-001` = 70.884、`best-002` = **66.851**。`save_top_k=10` 只按数值排序，新口径的 83 永远排不进前 10，结果是**后续 97 个 epoch 的最佳权重一个都不会被保存**，而训练看起来完全正常。

**为什么没有自动报警：** `ModelCheckpoint` 不会报错，`val/paper_loss` 也在正常下降，只是所有新 checkpoint 都落在 `save_top_k` 窗口之外。唯一的表征是 `checkpoints/` 目录里 `best-*` 的数量不再增长。

**修复：** 停训后直接改写 `last.ckpt` 里的 `ModelCheckpoint` 状态（`best_k_models={}`、`kth_best_model_path=''`、`best_model_path=''`、`best_model_score=None`），权重 / 优化器 / EMA shadow / LR 调度器状态全部保持不动，然后 resume。旧口径的三个 `best-*.ckpt` 文件保留在磁盘上，对应 R1 的 epoch 0–2。

**通用规则：** **任何改变 loss 权重、增删 loss 项、或改动验证口径的 resume，都必须同时清空 `ModelCheckpoint` 的历史。** 否则新值会在数量级上被旧值压制，且没有任何错误提示。

**另一个同源风险：** EMA 的 `decay` 也会随 checkpoint 恢复，因此「resume 时突然换 EMA 窗口」会被旧值静默覆盖。已在 `EMACallback.load_state_dict` 中改为**配置优先**，并在加载后重新断言 `self.ema.decay = self.decay`。

**解决建议（按代价排序）：**
1. 训练集同口径对照：在 train split 上重算 `pred_travel / gt_travel`。若训练集亦约 1.6×，属学到的策略偏差；若接近 1.0，属 state→速度泛化问题。这一步能区分损失设计与泛化能力，成本最低。
2. 给 Anchor 集合补零位移/低行程模式（如 0 m、1 m、2 m 档），消除候选行程下界的硬性抬升；需同步检查标签匹配与 mode 8 语义。
3. 多模态解码改为按置信度选 mode 而非多步去噪后的平均轨迹，验证低速偏差是否来自模式平均。
4. 损失侧加入低速加权或相对行程误差项；当前 trajectory 项为对称 L1，对「多走 15 m」与「少走 15 m」惩罚相同，模型没有抑制抢跑的动机。
5. 推理侧兜底（非训练修复）：对低速状态按速度阈值衰减预测行程，仅作部署期安全限制，不能替代上述修复。
